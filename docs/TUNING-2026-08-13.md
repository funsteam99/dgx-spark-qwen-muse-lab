## 三、NVFP4 + DFlash 判斷

對 DGX Spark 而言，NVFP4 + DFlash 是值得優先測試的高吞吐方向，但不是「只要打開兩個開關就必然最佳」，也不是硬體正常運作的必要條件。模型、draft、runtime 與 kernel 必須整套相容。

目前實況：

- Muse：DFlash 已啟用，但 target 與 draft 都是 K-quant GGUF，不是 NVFP4。
- Qwen：target 是 NVFP4，但 speculative decoding 是 MTP，不是 DFlash，而且日誌顯示 Marlin fallback。

真正要驗收 DGX Spark 原生 NVFP4 路徑，啟動日誌應能看到類似：

```text
FlashInferCutlassNvFp4LinearKernel
FLASHINFER_CUTLASS
```

若仍顯示 `Marlin`、`fallback` 或 GPU 不支援原生 FP4，不能宣稱完成 Spark 原生 NVFP4 最佳化。

候選 Muse 模型：

- `abstract-extraordinary/Muse-Glimmer-30B-NVFP4`

這是很新的社群模型，目前尚未在本機驗證。不可直接覆蓋現行服務；應以新容器及新 port 做 A/B。

參考資料：

## A.3 主要發現：瓶頸是 acceptance，不是上下文長度

```
corr(acceptance, decode t/s) = 0.973
corr(ctx,        decode t/s) = 0.155
```

依 acceptance 分四分位：

| 分位 | acceptance | decode 中位數 | ctx 中位數 |
|---|---|---:|---:|
| Q1 | 0.083–0.158 | 14.75 t/s | 85,188 |
| Q2 | 0.169–0.372 | 26.33 t/s | 23,404 |
| Q3 | 0.378–0.542 | 37.98 t/s | 38,187 |
| Q4 | 0.542–0.833 | **51.54 t/s** | 86,545 |

**Q4 的上下文中位數（86.5K）比 Q1（85.2K）還長，速度卻是 Q1 的 3.5 倍。**

這修正了正文第二節「長上下文同時滿載仍須持續觀察」所隱含的直覺：就 decode 吞吐而言，
上下文長度幾乎不是變因，acceptance 解釋了幾乎全部的變異。連帶的推論：

- **KV cache 量化（`-ctk/-ctv q8_0`）與縮減上下文，目前不是吞吐槓桿。** 只有在需要挪出
  統一記憶體給別的服務時才值得做。
- 正文第四節列的「DFlash `n-max`：8 / 12 / 15」A/B 優先度應該下修 —— n-max 調的是
  「要 draft 多少」，但資料顯示每次 draft 的命中率才是主導項。

## A.4 交叉比對：`funsteam99/dgx-spark-qwen-muse-lab`

`docs/EXPERIMENT.md`（GitHub，2026-08-12）記錄了部署驗證期的對照數字：

- 未啟用 DFlash：約 **7.5 tok/s**
- 啟用 DFlash（單次）：**23.1 tok/s**；併發負載下：24.1 tok/s
- 短控制 prompt 的 decode 加速比：**3.1×–3.2×**
- 當時 acceptance：70/285 與 69/300，約 **0.24**

**這個數字很重要，它限制了 A.2 那個「83.3% 浪費」的解讀。**
acceptance 僅 0.24 時 DFlash 仍有 3.1 倍加速，原因是 GB10 在 batch=1 時是記憶體頻寬
受限的：一次驗證 15 個 token 與驗證 1 個 token 的成本幾乎相同。因此**被丟棄的 draft
token 是「便宜的浪費」，83.3% 的 draft 丟棄率並不等於 83.3% 的效能損失。**

## A.5 待驗證假說：`--spec-draft-p-min`

現行啟動參數為 `n_max=15, n_min=0, p_min=0.00`（見容器啟動 log），
即不論把握多低都固定 draft 滿 15 個 token。

假說：把 `--spec-draft-p-min` 從 0 提高到 0.1–0.2，讓 draft model 在低信心時直接放棄，
可省下 draft model 的前向計算。

**但方向不確定**，必須實測而非直接套用：

- 省下的是 draft model 的計算成本（1.63 GB 的 draft，成本不高）
- 放棄的是那些「信心低但仍會被接受」的 draft
- 在頻寬受限、驗證幾乎免費的機器上，後者的損失有可能大於前者的節省

因此這是一個需要 A/B 的開放問題，不是一個確定的最佳化項。

## A.8 對 A.2 / A.3 的取樣範圍更正（同日追加）

初次解析時誤讀了 llama-server 的日誌時間前綴。該前綴格式為 `MM.SS.mmm.uuu`
（分.秒.毫秒.微秒），不是 `HH.MM.SS.mmm`。因此 `47.48.681.666` 是啟動後第 47 分 48 秒，
而非第 47 小時。

實際取樣範圍：

- 容器啟動時間：`2026-08-13T01:39:29Z`（09:39 CST），即本日將上下文調整為 131,072 的那次重啟。
- 解析當下：10:38 CST，容器運行 **59 分鐘**。
- A.2 的 97 個 task 全部落在這 59 分鐘內。

兩個後果：

1. **（正面）樣本乾淨。** 97 個 task 全部產生於 `-c 131072` 生效之後，沒有混入 32,768
   時期的資料。因此 A.2 是一份純粹的「調整後」快照，與 A.4 引用的 GitHub EXPERIMENT.md
   （32K 時期）恰好構成前後兩個世代，可以對照但不可直接混用。

2. **（負面）樣本不獨立。** 48K–131K 那一格的 54 個 task，實際上主要是**同一個對話從
   48K 逐步成長到 106,181 tokens** 的軌跡。樣本彼此高度自相關。這使 A.3 的兩個結論
   強度並不相同：

   - **「acceptance 主導 decode 吞吐」仍然成立。** 這接近機械性關係：每個驗證步驟接受
     愈多 token，每秒產出就愈高；r=0.973 只是把該關係量化。
   - **「上下文長度幾乎不影響 decode 速度」應降級為待檢驗的觀察，而非結論。** 在單一
     成長中的對話裡，ctx 與時間共變，本資料無法將兩者分離。

`~/muse_bench.py` 的設計正是為了補上這個缺口：固定 prompt、temp=0、seed=42，
在同一 arm 內以 8K / 32K 兩種受控長度取得彼此獨立的觀測。在該 A/B 完成前，
不應以 A.3 為由否決 KV cache 量化或上下文縮減 —— 只能說目前尚無證據支持它們是吞吐槓桿。

## A.9 Roofline 分析：吞吐上限從哪裡來（同日追加）

### A.9.1 模型實際結構

以 `~/gguf_meta.py` 直接解析 GGUF 標頭（不依賴啟動 log）：

| 項目 | Muse target | DFlash draft |
|---|---|---|
| 架構 | `muse-glimmer`，**稠密（非 MoE，731 個 tensor 中無 expert 張量）** | `dflash` |
| 層數 | 52 | 5 |
| embedding | 6656 | 6656 |
| FFN | 19968 | 19968 |
| attention head / KV head | 32 / **2**（GQA） | 32 / 8 |
| 張量總量 | **15.59 GiB = 16.7 GB** | 1.51 GiB |

稠密模型意味著**每產生一個 token，16.7 GB 的權重必須完整掃過一次**。

### A.9.2 頻寬天花板

GB10 規格記憶體頻寬 **273 GB/s**（128 GB LPDDR5X，256-bit，16 通道）。

```
16.7 GB / 273 GB/s  ->  每秒最多 16.3 次權重掃描
```

非投機解碼下一次掃描產出一個 token，故 **16.3 t/s 為理論上限**。
A.4 引用的無 DFlash 實測 7.5 t/s 約為規格峰值的 46%。

**吞吐 ≈ 掃描速率 × 每次掃描產出的 token 數。** 此模型與觀測一致：

- A.3 Q4 分位：51.5 t/s ÷ mean accepted len 7.35 = 7.0 次掃描/秒
- A.2 48K–131K 中位：34.8 t/s ÷ 7.35 = 4.7 次掃描/秒

這解釋了 A.3 為何會量到 r=0.973 —— acceptance 幾乎就是這條公式裡的乘數本身。
DFlash 並未讓硬體變快，它是讓每次掃描多帶出幾個 token。

### A.9.3 KV 流量：對 A.3 的第二次更正

A.3 曾主張 KV cache 量化「不是吞吐槓桿」。依實際結構計算，**該主張是錯的**。

每 token 的 KV 位元組（f16）：`52 層 × 2 KV head × 208 head_dim × 2（K 與 V）× 2 bytes = 86.5 KB`

| 上下文 | 權重 + KV = 每次掃描流量 | 理論掃描/秒 |
|---|---|---|
| ~0 | 16.7 GB | 16.3 |
| 32K | 19.5 GB | 14.0 |
| 106K | 16.7 + 9.2 = **25.9 GB** | 10.5 |
| 131K 滿載 | 16.7 + 11.4 = 28.1 GB | 9.7 |

在 106K 上下文時，KV 流量已超過權重流量的一半。
`-ctk q8_0 -ctv q8_0` 將其減半 → 每次掃描 25.9 GB 降至 21.3 GB，
**預測長上下文 decode 吞吐提升約 20%**。

由於本日已將上下文全開，實際運行就落在此區間，故此項為可實現值而非理論值。
本 build 的 `-DGGML_CUDA_FA_ALL_QUANTS=ON` 已含量化 KV 的 flash attention kernel，
無須重新編譯。代價：q8_0 KV 會引入極小的數值誤差，需在 A/B 時一併觀察輸出品質。

### A.9.4 對「原生 kernel」說法的更正

正文第三節關於 Marlin fallback 的論述**只適用於 Qwen（vLLM／NVFP4）**。
Muse 的映像檔建置參數為：

```
-DCMAKE_CUDA_ARCHITECTURES=121
-DGGML_CUDA=ON
-DGGML_CUDA_FA_ALL_QUANTS=ON
```

即 **Muse 本來就編譯為 GB10 sm_121 原生 kernel**，此處無待修正項。

需區分兩個不同概念：

1. **為本架構編譯的 kernel** —— Muse 已具備。
2. **使用 FP4 tensor core 的 kernel** —— llama.cpp 無此路徑（走 Q4_K dequant-and-dot）。

而 **batch=1 decode 為記憶體受限**，第 2 項對單串流吞吐幾乎無意義：瓶頸在等 DRAM
而非等乘法器。因此 NVFP4 對 Muse decode 的預期收益低；其潛在價值在 prefill 與多併發。

同時撤回一項過強的推論：先前曾據 46% 推論「kernel 尚有 1.5 倍空間」，此說不成立 ——
kernel 已是原生；273 GB/s 為規格峰值而 LPDDR5X 實際可達通常為規格的 70–80%，
真實天花板應接近 11–13 t/s；且該 7.5 t/s 量測本身帶有未知長度的 KV 流量。
**基礎掃描速率應視為已接近本機上限，不再列為槓桿。**

   必須同時檢查 acceptance 是否同步漂移。** 此條在後續 NVFP4 評估時直接適用。

## A.12 `-b/-ub` 結果，以及 A.9.3 錯誤的真正原因（2026-08-13 追加）

### A.12.1 `-b 4096 -ub 2048`：無效果，但結論有價值

| prefill（相同 prompt） | baseline | ub2048 |
|---|---|---|
| 8K（6,600 tok） | 303.1 t/s | 279.4 t/s |
| 32K（26,633 tok） | 289.7 t/s | 292.2 t/s |
| 87K（87,241 tok） | 262.0 t/s／338.4 s | 266.8 t/s／332.0 s |

加權 decode 17.175 → 17.641（+2.7%，低於雜訊底線）。

**健全性檢查通過**：加權 acceptance 0.154 → 0.155（+0.7%），符合預期 ——
`-b/-ub` 不改變數值精度，故 acceptance 應不動。此結果反向確認了 A.11.3 第 4 點：
kvq8 的 acceptance 跳動確實源於精度改變，而非隨機漂移。

**結論：prefill 不受矩陣形狀限制，而受 kernel 效率限制。**
無論餵入多大批次，穩定在約 290 t/s ≈ 17 TFLOP/s，遠低於本硬體算力。
`-ub` 不採用。

此結果**強化**了 NVFP4 的理由，並給出具體目標：將 prefill 自 290 t/s 往上推。
原生 FP4 tensor core 正是針對此類「算力未被利用」的情況。

### A.12.2 A.9.3 錯誤的真正原因（已證實）

自 GGUF 標頭直接讀出：

```
muse-glimmer.attention.sliding_window          2048
muse-glimmer.attention.sliding_window_pattern  [True, True, True, False, ...]
muse-glimmer.attention.key_length              128
muse-glimmer.attention.value_length            128
```

A.9.3 的 KV 計算有兩處錯誤，複合後高估約 6.5 倍：

1. head_dim 以 `6656 / 32 = 208` 推算，**實際為 128**（GGUF 明載）。高估 1.6 倍。
2. 假設 52 層全部保留完整 KV，**實際僅 13 層**。`sliding_window_pattern` 為
   「真真真假」循環，每四層僅一層全注意力，其餘三層只保留 2,048 tokens 滑動窗口。
   高估 4 倍。

正確數值：

| | A.9.3 所載 | 實際 |
|---|---|---|
| 每 token KV（全注意力層） | 86.5 KB | **13.3 KB** |
| 87,241 tokens 時 KV 總量 | 7.55 GB | **1.24 GB** |
| 佔每次掃描流量比例 | 31% | **7%** |
| 滑動窗口層 KV（固定） | 未計入 | 約 0.082 GB |

因此 q8_0 將 KV 減半僅省下 0.62 GB / 17.9 GB = **3.5%**，
而其在 attention kernel 中新增的解壓縮成本大於此值，淨值為負。
與 A.11.1 實測的 −9.9%（在雜訊範圍內的負值）一致。

**A.11.3 第 3 點所提的「窄讀取受延遲限制」假說應予撤回** ——
真正原因是 KV 總量本來就小，不是讀取效率問題。

### A.12.3 連帶解決 A.8 的懸案

A.3 原始觀察為「上下文長度幾乎不影響 decode 速度」，A.8 因樣本不獨立而將其降級。
A.12.2 為該觀察提供了結構性原因：**此模型的 KV 幾乎不隨上下文成長。**

即使開至滿的 131,072 tokens：

```
全注意力層 KV = 131,072 × 13.3 KB   = 1.75 GB
滑動窗口層 KV（固定）                = 0.08 GB
合計約 1.8 GB，相對於 16.7 GB 權重不足一成
```

**故 A.3 的原始觀察成立，A.9.3 的「更正」才是錯的。**
實務意義：本日將上下文調至 131K 的代價遠小於預期，
且 KV cache 量化在此架構上不具吞吐價值（其價值僅在節省記憶體，而記憶體並不緊張）。

## A.13 NVFP4 可行性：kernel 選擇已確認，GEMM 已實測（2026-08-13 追加）

正文第三節提出的驗收條件是「啟動日誌應能看到 `FlashInferCutlassNvFp4LinearKernel`」。
本節在**未下載任何模型權重**的情況下回答了該問題，並進一步實測了 kernel 的實際算力。

### A.13.1 backend 選擇：dense NVFP4 走 FLASHINFER_CUTLASS

vLLM 的 dense linear 路徑選擇邏輯位於
`vllm/model_executor/layers/quantization/utils/nvfp4_utils.py`：

```python
if current_platform.has_device_capability(100) and has_flashinfer():
    backend = FLASHINFER_CUTLASS
elif cutlass_fp4_supported():
    backend = VLLM_CUTLASS
elif is_fp4_marlin_supported():
    backend = MARLIN
```

`has_device_capability(100)` 是**最低門檻**檢查（`current_capability.to_int() >= capability`），
GB10 為 sm_121 → 121 >= 100 成立。

在本機 GPU 上實際執行（`nvcr.io/nvidia/vllm:26.03-py3`，未載入任何模型）：

```
capability      : DeviceCapability(major=12, minor=1)
has_cap(100)    : True
has_flashinfer  : True  (flashinfer 0.6.7+a79fb63c.nv26.03.cu132)
SELECTED BACKEND: NvFp4LinearBackend.FLASHINFER_CUTLASS
```

**結論：dense NVFP4 在本機選用 FLASHINFER_CUTLASS，非 Marlin。**

**Qwen 為何是 Marlin 也隨之澄清**：`Qwen3.6-35B-A3B` 是 MoE，走的是
`select_nvfp4_moe_backend()`，與 dense linear 路徑完全不同。
社群論壇上「NVFP4 在 GB10 上壞掉」的回報絕大多數屬於 MoE 情境
（vLLM issue #50925 標題即為 "NVFP4 MoE falls back to Marlin on sm_121"）。
**Muse 是稠密模型（見 A.9.1），不受此限。**

因此正文第三節「若仍顯示 Marlin 則不能宣稱完成最佳化」的驗收條件，
對 Muse 而言在 backend 選擇這一層已經通過。

### A.13.2 FP4 GEMM 微基準（Muse 實際層尺寸）

腳本 `~/fp4_gemm_bench.py`，以隨機張量在本機 GPU 實測：

| shape | M | K | N | BF16 | **FP4** | 加速 |
|---|---:|---:|---:|---:|---:|---:|
| ffn-up prefill | 2048 | 6656 | 19968 | 28.3 | **89.5** TFLOP/s | 3.16x |
| ffn-down prefill | 2048 | 19968 | 6656 | 30.6 | **73.4** | 2.40x |
| attn-qkv prefill | 2048 | 6656 | 6656 | 24.1 | **80.2** | 3.33x |
| ffn-up ubatch512 | 512 | 6656 | 19968 | 27.0 | **104.2** | 3.86x |
| **ffn-up decode** | **1** | 6656 | 19968 | **0.2** | **0.3** | 1.59x |

**FlashInfer CUTLASS 的 FP4 kernel 在 sm_121 上可正常執行且達 73–104 TFLOP/s。**

兩個對照：

1. **prefill 有真實餘裕。** llama.cpp 目前 prefill 的端到端等效算力約 17 TFLOP/s
   （290 tok/s，見 A.12.1），而 FP4 GEMM 達 90–104。即使 BF16 也有 28 ——
   代表現行 Q4_K 路徑連 BF16 的一半都未達到。
   **但此比較不對等**：17 是端到端等效值（含 attention、softmax、KV 寫入、取樣等
   非 GEMM 開銷），90 是純 GEMM。實際端到端增益將遠小於 5 倍，但方向明確。

2. **decode 不會受益，證據再次一致。** M=1 時 FP4 僅 0.3 TFLOP/s、BF16 0.2 ——
   兩者皆趴地，因為該處為記憶體受限（見 A.9.2）。這與 A.9.4 的推論、
   A.11 的實測結果完全一致。

微基準輸出的 `rel_err≈0.135` 不具意義：使用隨機張量配粗糙全域縮放，
真實模型有逐區塊校準的 scale。該數值不可作為品質訊號。

### A.13.3 對 NVFP4 路徑的更新後判斷

**值得做，但價值主張限定在 prefill。**

- prefill：87K prompt 現需 338 秒（262 tok/s）。GEMM 層有 3–4 倍餘裕。
- decode：預期持平或略降。若 DFlash 在 vLLM 接上則持平（約 17 t/s），
  若接不上則掉至 13 t/s 左右（社群回報 vLLM 單串流約 13 t/s）。

**驗收標準應為「prefill 大幅變快，且 decode 未變慢」，不可只看總吞吐。**
且依 A.11.3 第 4 點，換量化格式屬於改動數值的變更，必須同時檢查 acceptance 是否漂移。

### A.13.4 模型來源與下載

  取代正文第三節所列的 `abstract-extraordinary/...`。理由：Red Hat AI 為
  vLLM 生態的常規量化發布者，出處可追溯；若結果不佳，可排除「量化品質不良」

  （故自身不存這兩者）。**其對 NVFP4 量化 target 的相容性未經驗證** ——
  若綁定失效，預期表現為 acceptance 崩潰而非報錯，屬靜默失敗，必須主動檢查。

**磁碟：不需清理。** 下載總量約 27.4 GB，可用 81 GB。

## A.14 NVFP4 路徑暫停：runtime 對 aarch64 尚未成熟（2026-08-13 結案）

A.13 判定 NVFP4 值得一試（價值主張限定在 prefill）。實際查證後**暫停**，
原因不是硬體或模型，而是**沒有任何 runtime 能在 GB10 的 aarch64 上跑 Muse Glimmer**。

### A.14.1 時間線

| 事件 | 日期 |
|---|---|
| sglang 0.5.17 發布（PyPI 與 docker `latest-cu130`，NVIDIA playbook 指定版本） | 08-07/08 |
| Muse Glimmer 發布 | 08-10 |
| NIM `nim/meta/containers/muse-glimmer` 上架（Pre-Release） | 08-10，08-11 更新 |
| **Muse 支援合併進 sglang main**（commit #34262） | **08-11** |
| vLLM PR #51655（Add Muse Glimmer model support） | **至今未合併** |

**任何 08-11 之前建置的產物都不含 Muse 支援。**

### A.14.2 三條路徑的實測狀態

| 路徑 | 狀態 | 證據 |
|---|---|---|
| vLLM | **不可行** | PR #51655 未合併。本機實測：`nvcr.io/nvidia/vllm:26.03`（0.17.1）305 個架構無 muse；`vllm/vllm-openai:nightly`（0.23.1rc1，06-29 建）355 個架構無 muse，但 `dflash` 已是合法 speculative method。PR 討論串另記錄 SM120 Blackwell 的 CUDA 錯誤。 |
| SGLang | **僅 nightly** | PyPI 0.5.17 wheel 內 4,317 個檔案零命中 muse。`lmsysorg/sglang:latest-cu130` 建於 08-07（v0.5.17），早於合併日。唯一可用者為 `nightly-dev-cu13-20260813-273d978b`，arm64 壓縮 13.29 GiB。 |
| NIM | **不可行** | 狀態為 Pre-Release candidate；**僅認證 Linux/amd64 與 SM120**。已有回報：DGX Spark canary 以 TP=1 選中 NVFP4 路徑，但 **ARM64 runtime 的 profile run 失敗**。 |

**共同弱點是 aarch64。** 連 NVIDIA 官方容器都尚未跑通，社群 nightly 的成功機率不高。

### A.14.3 暫停決定與成本

若強行進行，需下載約 33 GiB（RadixArk 權重 18.34 + SGLang nightly image 13.29 +
assistant 剩餘），以實測對外頻寬 1.1 MB/s 計約 **8.6 小時**，
換取的是「decode 幾乎確定不變、prefill 可能變快」的不確定結果，
且執行環境為兩天大的 nightry build。**判定不划算，暫停。**

已下載的部分：

- `meta-models/Muse-Glimmer-30B-assistant`（DFlash draft head）——
  **僅下載 1,249,514,477 / 5,111,976,608 bytes（24%），且該檔案可能已損毀。**
  在切換 target（RedHatAI → RadixArk）而重啟下載器時，舊的下載行程未被完全終止，
  導致兩個行程同時以 `-C -` 寫入同一檔案。期間曾觀察到 `du` 回報 5.1G
  而 `ls -l` 同時回報 1.19G —— 此種落差正是多重寫入造成稀疏檔的徵狀。
  **重啟時應先刪除 `model.safetensors` 再以 `hf_pull.sh` 重新下載，
  不可直接續傳**（部分檔案無法用 HF 的整檔 sha256 驗證）。
  該檔僅 4,875 MB，重下約 75 分鐘。
- **未下載** RadixArk 權重與 SGLang image。

（教訓：`hf_pull.sh` 重啟前必須確認舊行程與其子 `curl` 皆已終止。
`pgrep -f hf_pull` 不會匹配到子行程的 `curl`，需一併清除。）

### A.14.4 正面發現（供日後重啟時使用）

1. **選定的組合是正確的。** NVIDIA 技術部落格描述的參考配置為
   「18 GB NVFP4 checkpoint paired with a 5 GB BF16 DFlash speculator」，
   與本次選定的 `RadixArk/Muse-Glimmer-NVFP4`（18.34 GiB，`quant_algo: MIXED_PRECISION`，
   ModelOpt 系，符合 NVIDIA playbook 要求的 `--quantization modelopt_fp4`）
   加上 assistant（4.875 GB）完全一致。
   （`RedHatAI/Muse-Glimmer-30B-NVFP4` 為 compressed-tensors 格式，21.80 GiB，
   與官方文件所述路徑不同，已放棄。）

2. **GB10 的 FP4 算力是真實存在的**（見 A.13.2 微基準：90–104 TFLOP/s）。
   NVIDIA 文件亦述 sm_121 為 native FP4。論壇上「NVFP4 在 GB10 上壞掉」的抱怨
   集中於 vLLM 的 **MoE** 路徑（issue #50925），與 dense 的 Muse 無關。
   **卡住的是 runtime 的 aarch64 支援，不是硬體。**

3. **NVIDIA 官方 SGLang on Spark playbook 已存在**（`~/dgx-spark-playbooks/nvidia/sglang`，
   本機 clone 已更新至 2026-07-29）。其模型支援矩陣中 NVFP4 項目全部通過
   （Llama-3.1-8B-FP4、Llama-3.3-70B-FP4、Qwen3-8B/14B/32B-FP4、Phi-4-multimodal-FP4），
   並註明「for NVFP4 models, add the `--quantization modelopt_fp4` flag」。
   指定容器為 `lmsysorg/sglang:latest-cu130`。

4. **SGLang 的 Muse Glimmer 啟動參數已知**（官方 cookbook）：

```
--model-path <NVFP4 path>
--reasoning-parser muse --tool-call-parser muse
--speculative-algorithm DFLASH
--speculative-draft-model-path meta-models/Muse-Glimmer-30B-assistant
--speculative-draft-model-quantization fp8
--kv-cache-dtype fp8_e4m3 --mem-fraction-static 0.9
--quantization modelopt_fp4
```

5. **`ubehera/sglang-spark`** 提供 sm_121a 原生的 `sgl-kernel` wheel（7.2 MB，
   供 pip 安裝路徑使用；docker 官方 image 已含可用 kernel，故非必需）。
   該 repo 另記錄 GB10 的統一記憶體 deadlock（「wedge」）與
   PyTorch 內建 NCCL 2.28.9 缺少 sm_121 cubin 的問題 —— 後者僅影響 TP>1，單卡不受影響。
